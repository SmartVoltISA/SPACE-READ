# SPACE-READ — физическая граница безопасности

## Цель

Защитить SPACE Core от любого внешнего пользователя, внешнего LLM, агента, приложения или ошибочного автоматического процесса.

Главный принцип:

> **Безопасность должна обеспечиваться не обещанием и не инструкцией для ИИ, а отсутствием физического пути к записи в Core.**

## 1. Зоны доверия

```text
┌─────────────────────────────────────────────┐
│                 SPACE CORE                  │
│  источник истины                            │
│  развитие организма                         │
│  внутренние данные                          │
│  права записи — доверенный контур           │
└──────────────────┬──────────────────────────┘
                   │ controlled publication
                   ▼
┌─────────────────────────────────────────────┐
│                SPACE-READ                   │
│  публичные данные / документация / схемы    │
│  machine-readable publication layer         │
└──────────────────┬──────────────────────────┘
                   │ read only
          ┌────────┼────────┐
          ▼        ▼        ▼
       HUMAN    RESEARCH    LLM

             НЕТ ОБРАТНОГО КАНАЛА
```

## 2. Физические ограничения

### 2.1 Нет credentials в SPACE-READ

В публичном слое не должно существовать:

- токенов доступа к Core;
- SSH-ключей Core;
- deploy keys с правом записи в Core;
- secrets, позволяющих публичному коду изменять Core;
- API-ключей внутренних сервисов;
- паролей или service-account credentials для Core.

### 2.2 Нет write API

Публичный интерфейс не должен иметь endpoint, команду или функцию вида:

`write_core()` / `update_core()` / `delete_core()` / `merge_to_core()`.

Текущий `AI_INTERFACE.md` описывает только концептуальные read-операции. Сетевой write API в SPACE-READ отсутствует.

### 2.3 Разделение полномочий

Учётные данные публикации READ не должны одновременно обладать правами изменения SPACE Core.

Рекомендуемое разделение:

- Core development identity;
- READ publication identity;
- READ CI identity;
- external read identity.

### 2.4 Однонаправленный publication pipeline

Будущий автоматический процесс:

`Core snapshot → validation → publication artifact → SPACE-READ`

Не:

`SPACE-READ → Core`.

### 2.5 Внешний ИИ изолирован

Внешний LLM может читать опубликованный слой, но не получает Core credentials, network route или API capability.

Даже при полной компрометации внешнего компонента его зона воздействия должна быть ограничена собственной сессией, собственной копией или предложением изменения.

## 3. Защита от ошибок владельца

Для Core должны быть предусмотрены:

- защищённая основная ветка;
- обязательная проверка изменений;
- резервные копии;
- версионирование;
- возможность восстановления;
- отдельная публикация наружу.

## 4. Внешние предложения

```text
EXTERNAL
   ↓
PROPOSAL
   ↓
VALIDATION
   ↓
REVIEW
   ↓
NEW PUBLICATION / CORE CHANGE
```

Внешнее предложение никогда не становится изменением Core напрямую.

## 5. Blast radius

Обязательный инвариант:

`X compromise ≠ SPACE Core compromise`.

## 6. GitHub-граница

`SPACE-READ` является публичным репозиторием. Публичные пользователи могут читать, делать fork и предлагать изменения, но это не даёт им права записи в оригинальный репозиторий или SPACE Core.

**Проверенное состояние на 2026-08-25:** ветка `main` существует, но GitHub branch protection для неё пока не включена. Это не даёт публичному пользователю push-доступа, однако защита ветки является следующим hardening-шагом для доверенного контура.

## 7. CI

SPACE-READ содержит локальный валидатор `scripts/validate_read.py` и GitHub Actions workflow `.github/workflows/validate-read.yml`.

Workflow явно ограничен:

```yaml
permissions:
  contents: read
```

Он проверяет структуру manifest/index, уникальность publication IDs, наличие целевых публикаций и распространённые credential-паттерны. Workflow не должен иметь credentials или операцию записи в Core.

## 8. Что нельзя обещать

Нельзя говорить, что система «абсолютно неуязвима».

Корректная формулировка:

**Мы проектируем систему так, чтобы внешний компонент не имел технического пути изменения Core.**

Если компрометация произойдёт внутри доверенного контура Core, это отдельная задача защиты внутреннего периметра.

## 9. Обязательная проверка перед подключением внешнего AI

- [ ] внешний LLM не имеет Core credentials;
- [x] публичный интерфейс не содержит write operation;
- [x] publication pipeline не принимает обратные команды;
- [ ] Core и READ имеют полностью разделённые deployment identities;
- [x] в опубликованной модели нет Core credentials;
- [ ] восстановление Core из backup проверено;
- [x] внешний fork не изменяет оригинал автоматически;
- [x] журнал публикаций сохраняет provenance.

## Главный инвариант

**Внешний мир может читать SPACE, анализировать его и предлагать. Внешний мир может создавать производные системы. Но внешний мир не должен иметь технической возможности непосредственно изменить, удалить или повредить эталонный SPACE Core.**
