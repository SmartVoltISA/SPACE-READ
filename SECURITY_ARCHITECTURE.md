# SPACE-READ — физическая граница безопасности

## Цель

Защитить SPACE Core от любого внешнего пользователя, внешнего LLM, агента, приложения или ошибочного автоматического процесса.

Главный принцип:

> **Безопасность должна обеспечиваться не обещанием и не инструкцией для ИИ, а отсутствием физического пути к записи в Core.**

## 1. Зоны доверия

```text
┌─────────────────────────────────────────────┐
│                 SPACE CORE                  │
│                                             │
│  источник истины                            │
│  развитие организма                         │
│  внутренние данные                          │
│  права записи — только у доверенного контура│
└──────────────────┬──────────────────────────┘
                   │
                   │ controlled publication
                   │  только наружу
                   ▼
┌─────────────────────────────────────────────┐
│                SPACE-READ                   │
│                                             │
│  публичные данные                            │
│  документация                               │
│  схемы                                      │
│  проверенные результаты                     │
│  read-only интерфейс                        │
└──────────────────┬──────────────────────────┘
                   │
                   │ read only
          ┌────────┼────────┐
          ▼        ▼        ▼
       HUMAN    RESEARCH    LLM

             НЕТ ОБРАТНОГО КАНАЛА
```

## 2. Физические ограничения

### 2.1 Нет credentials в SPACE-READ

В публичном слое не должно существовать:

- токенов доступа к Core;
- SSH-ключей Core;
- deploy keys с правом записи в Core;
- GitHub secrets, позволяющих публичному коду изменять Core;
- API-ключей внутренних сервисов;
- паролей или service-account credentials для Core.

Публичный репозиторий должен оставаться функционально бесполезным для попытки записи в Core даже в случае полного контроля над его содержимым.

### 2.2 Нет write API

Публичный интерфейс не должен иметь endpoint, команду или функцию вида:

`write_core()` / `update_core()` / `delete_core()` / `merge_to_core()`.

Read API получает данные. Он не принимает команды изменения организма.

### 2.3 Разделение учётных полномочий

Учётные данные, которыми публикуется SPACE-READ, не должны одновременно обладать правами изменения SPACE Core.

Лучший вариант — разные identity и разные credential scopes для:

- разработки Core;
- публикации READ;
- чтения READ;
- CI.

### 2.4 Однонаправленный publication pipeline

Будущий автоматический процесс должен работать только по схеме:

`Core snapshot → validation → publication artifact → SPACE-READ`

Не:

`SPACE-READ → Core`.

### 2.5 Внешний ИИ изолирован

Внешний LLM может читать опубликованный слой, но не получает credential, network route или API capability для Core.

Даже если внешний ИИ полностью скомпрометирован, его максимальная зона воздействия должна ограничиваться его собственной сессией, его собственной копией или предложением изменения.

## 3. Защита от ошибок владельца

Нельзя рассчитывать только на осторожность человека.

Для Core необходимо предусмотреть:

- защищённую основную ветку;
- обязательную проверку изменений;
- резервные копии;
- версионирование;
- возможность восстановления предыдущего состояния;
- отдельную публикацию наружу.

## 4. Защита от вредоносного внешнего контента

Публикация в READ не должна автоматически означать принятие любого внешнего предложения.

Предложение извне проходит отдельный контур:

```text
EXTERNAL
   │
   ▼
PROPOSAL
   │
   ▼
VALIDATION
   │
   ▼
REVIEW
   │
   ▼
CORE CHANGE
```

Внешнее предложение никогда не становится изменением Core напрямую.

## 5. Blast radius

Каждый внешний компонент должен иметь минимально возможный радиус поражения.

Если компонент `X` взломан, должно быть возможно утверждать:

`X compromise ≠ SPACE Core compromise`.

Это обязательный архитектурный инвариант.

## 6. GitHub-граница

Публичность `SPACE-READ` означает доступ к опубликованному содержимому. Fork или изменение fork не изменяет оригинальный репозиторий.

Однако одного факта Public недостаточно для полной безопасности. Реальная защита Core должна обеспечиваться разделением репозиториев, полномочий, credentials и каналов публикации.

## 7. Что нельзя обещать

Нельзя говорить, что система «абсолютно неуязвима». Корректная формулировка сильнее технически:

**Мы проектируем систему так, чтобы внешний компонент не имел технического пути изменения Core.**

Если компрометация произойдёт в доверенном контуре Core, это уже отдельная задача защиты внутреннего периметра.

## 8. Обязательная проверка перед запуском внешнего AI

До подключения первого внешнего LLM должны быть подтверждены:

- [ ] внешний LLM не имеет Core credentials;
- [ ] публичный интерфейс не содержит write operation;
- [ ] publication pipeline не принимает обратные команды;
- [ ] Core и READ имеют разделённые права;
- [ ] секреты Core отсутствуют в READ;
- [ ] восстановление Core из версии/backup проверено;
- [ ] внешний fork не способен изменить оригинал;
- [ ] журнал публикаций сохраняет происхождение данных.

## Главный инвариант

**Внешний мир может читать SPACE. Внешний мир может предлагать. Внешний мир может создавать свои производные системы. Но внешний мир не должен иметь технической возможности непосредственно изменить, удалить или повредить эталонный SPACE Core.**
